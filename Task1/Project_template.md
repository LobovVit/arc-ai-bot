# Проект: RAG Telegram-бот для QuantumForge Software

## Задание 1. Исследование моделей и инфраструктуры

### Контекст

QuantumForge Software --- финско-эстонская продуктовая компания с
SaaS-платформой Digital Twin. Корпоративная база знаний распределена по
GitHub (Markdown/MDX), Confluence, PDF-спецификациям и Google Docs. Цель
--- внедрить Telegram-бота на базе Retrieval-Augmented Generation (RAG),
который: - быстро и точно отвечает на вопросы сотрудников **на основе
базы знаний**; - **честно говорит «Я не знаю»**, если ответ не найден в
источниках; - выявляет пробелы в документации (частые «Я не знаю» /
слабые источники); - снижает нагрузку на тимлидов, старших разработчиков
и поддержку; - упрощает подготовку к SOC 2 аудитам (актуальные политики,
владельцы, контроль изменений).

### Заказчики и пользователи

-   **Заказчики:** CTO/Head of Engineering, GRC/Security (SOC 2),
    Support Lead, HR (онбординг)
-   **Пользователи:** разработчики, саппорт, менеджеры/аналитики, новые
    сотрудники
-   **Ограничения:** часть документов конфиденциальна; обязательны
    ссылки на источники; SLA ответа 2--10 сек; мультиязычность EN/RU

## 1) LLM: локальные HF vs облачные OpenAI / YandexGPT

**Качество** - Облачные LLM (OpenAI/YandexGPT) стабильно сильнее в
reasoning и структурировании ответов. - Локальные HF
(Llama/Mistral/Qwen) требуют подбора модели и квантизации; без
донастройки качество ниже.

**Скорость** - Облако масштабируется провайдером; есть сетевой RTT. -
Локально зависит от GPU; на CPU для Telegram-чата может быть медленно.

**Стоимость владения** - Облако: оплата за токены, минимальный DevOps. -
Локально: CAPEX/OPEX на GPU + сопровождение.

**Развёртывание** - Облако --- самый быстрый time-to-market. - Локально
--- выше сложность MLOps.

**Вывод:** для пилота --- облачная LLM с провайдер-агностичным
интерфейсом для будущей миграции на on‑prem.

------------------------------------------------------------------------

## 2) Эмбеддинги: Sentence-Transformers (локально) vs OpenAI Embeddings (облако)

**Скорость индексации** - Облако --- быстрее на старте и
масштабируется. - Локально --- зависит от ресурсов (ускоряется GPU).

**Качество поиска** - Облачные эмбеддинги часто дают лучшее многоязычное
качество. - Локальные --- компромисс для privacy-first сценариев.

**Стоимость** - Облако --- дешево за токены, нет расходов на железо. -
Локально --- инфраструктурные затраты и поддержка.

**Вывод:** при допустимости передачи текстов --- облачные эмбеддинги;
иначе --- локальные.

------------------------------------------------------------------------

## 3) Векторная БД для Go: Qdrant vs ChromaDB vs FAISS

**Qdrant (для Go)** - Плюсы: отдельный сервис, HTTP/gRPC
API, фильтры по метаданным, персистентность, прод‑готовность. - Минусы:
дополнительный сервис (норма для продакшна).

**ChromaDB (как сервис)** - Плюсы: простой старт, коллекции/метаданные,
персистентность. - Минусы: интеграция из Go через HTTP‑клиент.

**FAISS** - Плюсы: быстрый ANN‑движок. - Минусы: библиотека, а не БД; в
Go высокая сложность (CGO). Практичнее выносить в отдельный
Python‑сервис.

**Вывод:** для Go‑реализации выбрать **Qdrant**.

## 4) Рекомендуемая конфигурация сервера

**Пилот (облако LLM/эмбеддинги + локально Qdrant/бот):** - CPU: 4--8
vCPU, RAM: 16--32 GB, Disk: NVMe 200--500 GB, GPU: не требуется

**Гибрид (локальные эмбеддинги):** - CPU: 8--16 vCPU, RAM: 32--64 GB,
Disk: NVMe 500 GB--1 TB, GPU: опционально 1×16--24 GB

**Полный on‑prem (локальная LLM):** - CPU: 16--32 vCPU, RAM: 128 GB,
Disk: NVMe 1--2 TB, GPU: 1×24--48 GB

## Итоговые варианты и выбор

**A) Быстрый запуск:** облачная LLM + облачные эмбеддинги + Qdrant\
**B) Гибрид (рекомендуемый):** облачная LLM + (локальные эмбеддинги для
чувствительных данных) + Qdrant\
**C) Полный on‑prem:** локальная LLM + локальные эмбеддинги +
Qdrant/Chroma\
**D) Гибрид с FAISS:** Go‑бот + Python‑RAG (FAISS) как сервис

**Рекомендуемое решение:** Вариант B --- баланс приватности, качества и
time‑to‑market.
