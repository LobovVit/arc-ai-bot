# Проект: RAG Telegram-бот для QuantumForge Software

## Задание 1. Исследование моделей и инфраструктуры

### Контекст

QuantumForge Software — финско-эстонская продуктовая компания с SaaS‑платформой Digital Twin.
Корпоративная база знаний распределена по GitHub (Markdown/MDX), Confluence, PDF‑спецификациям и Google Docs.

Цель — внедрить Telegram‑бота на базе Retrieval‑Augmented Generation (RAG), который:
- быстро и точно отвечает на вопросы сотрудников **на основе базы знаний**;
- **честно говорит «Я не знаю»**, если ответ не найден в источниках;
- выявляет пробелы в документации (частые «Я не знаю» / слабые источники);
- снижает нагрузку на тимлидов, старших разработчиков и поддержку;
- упрощает подготовку к SOC 2 аудитам (актуальные политики, владельцы, контроль изменений).

### Заказчики и пользователи

- **Заказчики:** CTO/Head of Engineering, GRC/Security (SOC 2), Support Lead, HR (онбординг)
- **Пользователи:** разработчики, саппорт, менеджеры/аналитики, новые сотрудники
- **Ограничения:** часть документов конфиденциальна; обязательны ссылки на источники; SLA ответа 2–10 сек; мультиязычность EN/RU; Telegram как основной интерфейс

## 1) LLM: локальные HF vs облачные OpenAI / YandexGPT

**Качество ответов**
- Облачные LLM (OpenAI/YandexGPT) обычно сильнее в reasoning и следовании инструкциям.
- Локальные HF (Llama/Mistral/Qwen) требуют подбора модели/квантизации; без донастройки качество может быть ниже.

**Скорость**
- Облако масштабируется провайдером; есть сетевой RTT.
- Локально скорость зависит от GPU; на CPU для Telegram‑чата может быть медленно.

**Стоимость владения**
- Облако: OPEX за токены, минимум DevOps.
- Локально: CAPEX/OPEX на GPU + сопровождение (MLOps/мониторинг/обновления).

**Развёртывание**
- Облако — самый быстрый time‑to‑market.
- Локально — выше сложность эксплуатации.

**Вывод:** для пилота — облачная LLM с провайдер‑агностичным интерфейсом (с возможностью миграции on‑prem при требованиях к полной изоляции данных).

---

## 2) Эмбеддинги: Sentence‑Transformers (локально) vs OpenAI Embeddings (облако)

**Скорость создания индекса**
- Облако — быстро, но зависит от квот/rate‑limit.
- Локально — предсказуемо по времени, без внешних ограничений (CPU/GPU).

**Качество поиска**
- Облачные эмбеддинги часто дают выше качество (особенно multi‑lingual).
- Локальные Sentence‑Transformers дают достаточное качество при корректном чанкинге и метаданных.

**Стоимость владения**
- Облако — оплата за токены + риск ограничений.
- Локально — инфраструктурные затраты, но нулевая стоимость за запрос.

**Вывод (под новые вводные):** выбираем **локальные эмбеддинги (Sentence‑Transformers)**, чтобы не отправлять документы наружу и не зависеть от rate‑limit/квот.

Рекомендуемая модель:
- `sentence-transformers/all-MiniLM-L6-v2` (384 dim)

## 3) Векторные базы: ChromaDB vs FAISS (+ выбор для Go)

**FAISS**
- Плюсы: быстрый ANN‑поиск.
- Минусы: это библиотека, а не БД; персистентность/метаданные/операционка — на вас; в Go — сложнее (CGO).

**ChromaDB**
- Плюсы: быстрый старт, коллекции и метаданные, персистентность.
- Минусы: чаще dev‑ориентированное решение; прод‑эксплуатация требует аккуратности.

**Qdrant (выбран для реализации на Go)**
- Плюсы: прод‑готовый сервис, персистентность, фильтры по метаданным, удобный REST/gRPC API для Go.
- Минусы: отдельный сервис (нормально для продакшна).

**Вывод:** для Go‑реализации выбираем **Qdrant**.

---

## 4) Рекомендуемая конфигурация сервера

**Пилот (облачная LLM + локальные эмбеддинги + Qdrant + Telegram‑бот):**
- CPU: 4–8 vCPU
- RAM: 16–32 GB
- Disk: NVMe 200–500 GB
- GPU: не требуется

**Полный on‑prem (локальная LLM + локальные эмбеддинги):**
- CPU: 16–32 vCPU
- RAM: 128 GB
- Disk: NVMe 1–2 TB
- GPU: 1×24–48 GB (зависит от модели)

---

## Итоговые варианты и выбор

**A) Облачная LLM + облачные эмбеддинги + Qdrant** — быстро, но риск rate‑limit и отправка контента наружу.  
**B) Облачная LLM + локальные эмбеддинги + Qdrant (рекомендуемое)** — баланс качества, приватности и стабильности.  
**C) Полный on‑prem (LLM+эмбеддинги локально) + Qdrant** — максимум приватности, выше стоимость/сложность.

**Рекомендуемое решение:** Вариант **B**.

## Решение по векторной БД

Выбираем **Qdrant**, потому что это прод‑готовая векторная БД с персистентностью, фильтрами по метаданным и удобной интеграцией из Go.
